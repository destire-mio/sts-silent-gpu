# CPU/GPU 一致性检查与完整测速

## 已确认的结果

2026 年 10 月 18 日，修复版本 `bc5b225dd7506ee31ada00d03dbca697497ab5d7` 在单张 Tesla V100-SXM2-16GB 上通过原生 CPU/GPU 严格对照。原测试及其比较逻辑未修改，固定路线输入也未修改。

| 检查 | 覆盖范围 | 结果 |
|---|---|---|
| 固定深层路线 | 12 个种子，15,038 次决策，每步比较 | 通过 |
| 随机运行 | 33 个环境 × 256 批，共 8,448 个批次槽位 | 通过 |
| 生命周期 | 终局重置、前缀回放、克隆、部分槽位推进、决策上限、种子耗尽与补充 | 通过 |
| 比较内容 | 完整 `Game` 字节、全部观测与状态数组、奖励、历史、候选动作 | 一致 |

这证明上述测试覆盖内的一致性，不能推广为所有游戏轨迹均已穷尽验证。神经网络浮点输出另有容差检查，不能与游戏状态的逐字节比较混为一谈。

Slurm 作业 `3507` 的构建耗时为 **7:50.57**，包括 GPU 静态库、原生对照程序及 CPU Python 模块；原生对照运行 **28.35 秒**，最终退出码 `0`。这是该次构建的墙钟时间。

## 修复了什么

### 未初始化的填充位和字节

严格比较首先发现 `CardQueueItem` 高 4 位、`ActionManager` 对齐字节及 `Event` 对齐字节不同。为这些填充位置增加显式零初始化，并补齐 `Event` 尾部填充。`sizeof(Game)` 保持 **37,872 字节**。

对应提交：`52d813a`、`73c04c4`。没有跳过这些字节或降低原生比较要求。

### GPU 生成代码错误地写入伤害来源和目标

在种子 `202610230000`、第 36 层、第 875 次决策（零起始索引 874），打出 Die Die Die 触发 Spiker 的 7 点荆棘反伤：CPU 将玩家格挡从 12 扣至 5，GPU 却让 Exploder 额外损失 7 点生命。

检查 Clang 21.1.7 的产物发现，LLVM 中间代码正确保存了 `Effect` 的类型、来源和目标；对应 PTX 却将这些字段写成零。独立的 32 线程最小复现得到：

| 编译方式 | 错误字段数 |
|---|---:|
| 原 `-O3` 参数 | 95 |
| `-O3`，设备端增加 `-fno-slp-vectorize` | 0 |

`bc5b225` 保留 `-O3`、RDC 和 inline threshold 5，在设备编译中关闭 SLP 向量化。游戏规则、动作顺序、RNG 和固定路线保持原样。`ce11724` 增加 `test_cuda_effect_fields` 回归测试，并使无需 Toolkit 的 PTX 检查使用相同编译参数。

## 测量状态

严格原生对照通过后，已提交单卡完整检查与测速作业 `3510`，源码为 `ce11724ed7612eaecd2a6b6e69e7b7b0aacd842a`。计划覆盖 Python 接口、8,721 个 E2 存档前缀、采样器对照、随机与固定深层模拟吞吐、CPU 基线、单卡推理和 PPO 更新。其最终结果尚未写入本节。

历史随机测速对应旧版本，见[原测速报告](gpu-benchmark-2026-10-18.md)。该版本后来发现一致性问题，不能用旧速度代替修复版本的实测。
